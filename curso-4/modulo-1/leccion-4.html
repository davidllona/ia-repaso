El tipo de dato (dtype): enteros, decimales y por qué importan los bytes

Tienes las notas de un usuario guardadas como enteros (5, 3, 4) y les sumas un bonus guardado como decimales (0,5; 0,5; 0,5). ¿Qué tipo tiene el resultado? ¿Y qué ocurre si le pides la media al tensor de enteros?

Analogía

El dtype es el tamaño de la casilla donde se guarda cada número. Una casilla de 1 byte (uint8) solo admite del 0 al 255: perfecta para el brillo de un píxel de una carátula (o para 1–5 estrellas), inútil para un peso decimal. Una de 8 bytes (float64) guarda muchos decimales, pero ocupa el doble que una de 4 y casi nunca hace falta para redes neuronales. Elegir el tipo es elegir entre precisión y memoria.

Ejemplo numérico · cuánto ocupa un catálogo de carátulas según el tipo

Imagina que Netflix guarda 60 000 carátulas en miniatura de 28 × 28 píxeles en gris (cifras inventadas para el ejemplo; son justo las medidas del conjunto MNIST de dígitos que usa el curso original, que aquí no se descarga porque no hay internet, pero el cálculo es válido).

  1. Elementos: 60 000 · 28 · 28 = 60 000 · 784 = 47 040 000 números.
  2. En uint8 (1 byte): 47 040 000 bytes ≈ 47 MB. Es como se guardan los píxeles originales.
  3. En float32 (4 bytes): 47 040 000 · 4 = 188 160 000 bytes ≈ 188 MB.
  4. En float64 (8 bytes): ≈ 376 MB: el doble que float32 sin ninguna ventaja para la red.

Ojo · el error del dtype, tres caras

Los problemas de tipo se presentan de tres maneras que verás constantemente. (1) Media de enteros: torch.tensor([1, 2, 3]).mean() falla con «Input dtype must be either a floating point or complex dtype. Got: Long»; convierte antes con .float(). (2) Producto de matrices con tipos distintos: «expected m1 and m2 to have the same dtype, but got: float != long int». (3) Pérdidas de clasificación: en el módulo 5 verás que CrossEntropyLoss espera las etiquetas como int64 (Long) y las predicciones como float32; pasarle etiquetas float32 da otro error de tipo. Regla: datos y parámetros en float32, etiquetas de clase en int64.

3 · El tipo de dato (dtype): cómo se deduce, cómo se cambia y qué errores da

Para qué sirve Ver qué dtype elige PyTorch, forzar uno con dtype=, convertir con .float() / .long(), entender qué tipo sale al mezclar tipos y provocar el error típico de pedir la media de enteros.

import torch

a = torch.tensor([1, 2, 3])
b = torch.tensor([1.0, 2.0, 3.0])
c = torch.tensor([True, False, True])
d = torch.tensor([1, 2, 3], dtype=torch.float32)
print(a.dtype, b.dtype, c.dtype, d.dtype)
print(a.type(), b.type())

print("a.float():", a.float(), a.float().dtype)
print(".long() trunca:", torch.tensor([1.5, 2.7, -0.9]).long())
print("int + float ->", (a + b).dtype)
print("int / 2     ->", a / 2, (a / 2).dtype)
print("int // 2    ->", a // 2)
print("bool a int  :", c.int(), c.sum())
print("bytes por número:", a.element_size(), b.element_size(), torch.zeros(1, dtype=torch.float64).element_size())
print("bytes de a y b  :", a.nbytes, b.nbytes)

try:
    a.mean()
except RuntimeError as err:
    print("Error:", err)
print(a.float().mean())

Por defecto, enteros → int64, decimales → float32. La conversión con .long() de [1.5, 2.7, −0.9] da [1, 2, 0]: truncar acerca al cero, así que −0,9 queda en 0 (no en −1). a / 2 devuelve [0.5, 1.0, 1.5] en float32 mientras que a // 2 da [0, 1, 1]. Los bytes cuadran: 3 enteros de 8 bytes = 24 bytes y 3 decimales de 4 bytes = 12 bytes. Y mean() sobre int64 falla con «Input dtype must be either a floating point or complex dtype. Got: Long»: una media casi nunca es un entero, así que PyTorch exige que antes conviertas. Es el mismo tipo de error de Long/Float que verás en las pérdidas de los módulos siguientes.
