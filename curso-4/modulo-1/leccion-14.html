El grafo de cómputo dinámico: hojas, grad_fn y qué recibe gradiente

Cuando llamas a backward(), ¿cómo sabe PyTorch por dónde ir, qué tensores reciben gradiente y por qué algunos devuelven None?

El «cuaderno de apuntes» es un grafo: cada tensor es un nodo y cada operación une unos nodos con otros. Hay dos clases de nodos:

  • Hojas (leaf tensors): los tensores que creas tú directamente (w, b, los datos). Si tienen requires_grad=True, su derivada se guarda en .grad. x.is_leaf es True.
  • Nodos intermedios: los resultados de operaciones (m = w * x, z = m + b…). Tienen un grad_fn: el objeto que sabe calcular la derivada local de la operación que los creó (MulBackward0 para una multiplicación, AddBackward0 para una suma, PowBackward0 para una potencia…). No guardan su .grad salvo que lo pidas con retain_grad(), porque casi nunca hace falta y ocupa memoria.

Una regla importante: un resultado requiere gradiente si alguna de sus entradas lo requiere. Por eso y = 3 * x ** 2 + 2 * x + 1 tiene requires_grad=True sin que lo hayas puesto: lo hereda de x.

Es dinámico: el grafo se construye cada vez que ejecutas

En PyTorch el grafo no se define de antemano: se construye operación a operación mientras tu código se ejecuta (se dice define-by-run) y se tira después del backward(). Eso permite usar if, for y funciones normales de Python dentro del cálculo. En el fragmento 19 la función f hace \( x^2 \) si \( x>0 \) y \( -3x \) si no: con \( x=2 \) el grafo contiene una potencia y la derivada es 4; con \( x=-2 \) contiene una multiplicación y la derivada es −3. Recuerda (Curso 3)

En TensorFlow, tf.function traza la función una vez y reutiliza el grafo (los if sobre tensores requieren AutoGraph; un print sale solo al trazar). En PyTorch normal no hay trazado: cada llamada ejecuta Python de verdad, así que un print sale siempre. (PyTorch también tiene compilación opcional con torch.compile, que no necesitas ahora.)

retain_graph: por qué «el grafo se libera»

Tras cada backward(), PyTorch libera los valores intermedios guardados para ahorrar memoria. Por eso una segunda llamada a backward() sobre el mismo resultado falla con «Trying to backward through the graph a second time…». Si de verdad la necesitas, la primera llamada debe ser backward(retain_graph=True). En un entrenamiento normal nunca hace falta: en cada iteración se calcula una pérdida nueva con un grafo nuevo. Si te aparece este error en un bucle, casi siempre es que reutilizas un tensor calculado fuera del bucle (y que depende de parámetros) dentro de él.

19 · El grafo es dinámico: if en tu código, grad_fn y retain_graph

Para qué sirve Comprobar que PyTorch construye el grafo mientras ejecutas tu código (con if normales), explorar el grafo con grad_fn y next_functions, y ver el error «backward through the graph a second time».

import torch

def f(x):
    if x > 0:
        return x ** 2
    return -3 * x

for valor in [2.0, -2.0]:
    x = torch.tensor(valor, requires_grad=True)
    y = f(x)
    y.backward()
    print(f"x = {valor:5.1f} | y = {y.item():5.1f} | grad_fn = {type(y.grad_fn).__name__:12s} | dy/dx = {x.grad.item()}")

a = torch.tensor(2.0, requires_grad=True)
c = (a * 3 + 1) ** 2
print(c.grad_fn.name())
print([fn.name() for fn, _ in c.grad_fn.next_functions])
c.backward(retain_graph=True)
c.backward()
print("a.grad tras dos backward:", a.grad)
try:
    c.backward()
except RuntimeError as err:
    print("Error:", str(err)[:60], "...")

El mismo código sigue dos caminos distintos: con \( x=2 \) usa PowBackward0 y la derivada es \( 2x = 4 \); con \( x=-2 \) usa MulBackward0 y la derivada es −3. El grafo no se «definió» antes: se construyó al ejecutar, una vez por cada llamada (esto se llama define-by-run). Para \( c = (3a+1)^2 \) en \( a=2 \): \( dc/da = 2(3a+1)·3 = 42 \) por llamada, y tras dos llamadas a.grad = 84 (se acumula, como verás en detalle más abajo). El tercer backward() falla con «Trying to backward through the graph a second time…»: tras cada backward() PyTorch libera los tensores intermedios para ahorrar memoria, salvo que pidas retain_graph=True.
