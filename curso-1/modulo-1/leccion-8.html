En la demo bajas max_iter a 0: el modelo casi no aprende. ¿Fallará solo en test, o también en train?

En los dos. Un modelo que apenas aprende ni acierta el entrenamiento: underfitting (61 % / 60 %). El overfitting es lo contrario: brilla en train y se hunde en test. Para no depender de un reparto de suerte se rota el test (validación cruzada) y se ajustan los hiperparámetros con GridSearchCV.

Repartir los datos y mirar las dos notas

Un reparto habitual es 80 % train (los apuntes: el modelo aprende) y 20 % test (el examen final: se mira una sola vez). Para decidir durante el desarrollo (¿K = 3 o 7?) se usa un tercer conjunto, validation. Si miras el test, cambias algo y vuelves a mirar, deja de ser «datos desconocidos».

Comparando las notas de train y test se ven tres situaciones:

SituaciónTrainTestQué pasa
Underfitting61 %60 %Demasiado simple: ni entiende el train.
Buen ajuste86 %84 %Parecido en lo visto y lo nuevo: generaliza.
Overfitting99 %68 %Ha memorizado ruido y casos sueltos.
Analogía

Tres amigos te recomiendan películas. Uno memoriza las que viste y te las repite (overfitting). Otro solo sabe que «a todos les gusta la acción» (underfitting). El que entiende por qué te gustan acierta con los estrenos: generaliza.

3 aciertos de 4: accuracy = 3 / 4 = 75 %. Pero la accuracy no dice cómo falla. En el fragmento 19 (171 pacientes): 62 malignos detectados, 105 benignos correctos y 2 + 2 errores → 167 / 171 = 0,977. Los 2 malignos dados por benignos son el error grave: para verlo existe la matriz de confusión.

En tres líneas

  • Train para aprender, validation para decidir, test una sola vez al final. Primero separa, luego escala.
  • Train alto + test bajo = overfitting; los dos bajos = underfitting; parecidos y buenos = generaliza.
  • El patrón de siempre: X + y → train/test → crear (≠ entrenar) → fit → predict → evaluar → validación cruzada → GridSearchCV → Pickle.

8 · Ver el sobreajuste con números

Para qué sirve Comprobar con código lo que viste en el experimento: al subir la complejidad el error de train baja siempre, pero el de test, a partir de cierto punto, se dispara.

import numpy as np

rng = np.random.default_rng(42)

def verdad(x):
    return 0.8 * np.sin(2.4 * x) + 0.25 * x

# 20 puntos para entrenar y 200 para probar, con ruido
x_train = rng.uniform(-1, 1, 20)
y_train = verdad(x_train) + rng.normal(0, 0.2, 20)
x_test = rng.uniform(-1, 1, 200)
y_test = verdad(x_test) + rng.normal(0, 0.2, 200)

for grado in (1, 3, 12):
    coef = np.polyfit(x_train, y_train, grado)
    error_train = np.mean((np.polyval(coef, x_train) - y_train) ** 2)
    error_test = np.mean((np.polyval(coef, x_test) - y_test) ** 2)
    print(f"grado {grado:2d} | error train = {error_train:.3f} | error test = {error_test:.3f}")

21 · Validación cruzada y Hyperparameter Tuning con GridSearchCV

Para qué sirve Medir un modelo con varias «pruebas» rotando el bloque de validación, y probar sistemáticamente combinaciones de hiperparámetros para quedarse con la mejor. Reutiliza el reparto del fragmento 19.

from sklearn.datasets import load_breast_cancer
from sklearn.model_selection import train_test_split, cross_val_score, GridSearchCV
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.svm import SVC

datos = load_breast_cancer()
X_train, X_test, y_train, y_test = train_test_split(
    datos.data, datos.target, test_size=0.3, stratify=datos.target, random_state=42)

# El pipeline mete el escalador DENTRO de la validación: se reajusta en cada vuelta
modelo = make_pipeline(StandardScaler(), SVC())

# Validación cruzada: varias pruebas rotando el bloque de validación
for k in (4, 5):
    notas = cross_val_score(modelo, X_train, y_train, cv=k)
    print(f"cv={k}: notas = {notas.round(3)} | media = {notas.mean():.3f}")

# Hyperparameter tuning: probar combinaciones de C y gamma
rejilla = {"svc__C": [0.1, 1, 10], "svc__gamma": [0.001, 0.01, 0.1]}
busqueda = GridSearchCV(modelo, rejilla, cv=5)
busqueda.fit(X_train, y_train)

print("combinaciones probadas:", len(busqueda.cv_results_["params"]))
for p, nota in zip(busqueda.cv_results_["params"], busqueda.cv_results_["mean_test_score"]):
    print(p, round(nota, 3))
print("mejor:", busqueda.best_params_, "->", round(busqueda.best_score_, 3))
print("nota final en test:", round(busqueda.score(X_test, y_test), 3))

4 · StandardScaler: a mano y con Scikit-learn

Para qué sirve Entender qué hace exactamente StandardScaler comprobando que su resultado coincide con la fórmula z = (x − μ) / σ calculada a mano.

import numpy as np
from sklearn.preprocessing import StandardScaler

edades = np.array([[20], [30], [40]])

# A mano: (x - media) / desviación típica
manual = (edades - edades.mean()) / edades.std()

# Con scikit-learn
escalador = StandardScaler()
auto = escalador.fit_transform(edades)

print("media  :", escalador.mean_)
print("desv.  :", escalador.scale_.round(3))
print("manual :", manual.ravel().round(3))
print("sklearn:", auto.ravel().round(3))

5 · Feature engineering: de la fecha a la estación

Para qué sirve Crear una variable más informativa (la estación) a partir de otra casi inútil para el modelo (la fecha exacta), igual que en el proyecto de lluvia de Australia.

import pandas as pd

fechas = pd.DataFrame({
    "Fecha": pd.to_datetime(["2026-01-15", "2026-04-10", "2026-07-22", "2026-10-05"])
})

def estacion(mes):
    if mes in (12, 1, 2):
        return "Summer"
    if mes in (3, 4, 5):
        return "Autumn"
    if mes in (6, 7, 8):
        return "Winter"
    return "Spring"

fechas["Mes"] = fechas["Fecha"].dt.month
fechas["Estacion"] = fechas["Mes"].apply(estacion)
print(fechas)

10 · StreamFlix: limpiar la edad y crear features con Pandas

Para qué sirve Los pasos 4 y 5 del ciclo de vida con datos de juguete: arreglar una columna sucia (25, 34, NULL, «treinta», 450) y convertir una lista de películas vistas en una fila por usuario con minutos medios, género favorito y días entre películas.

import numpy as np
import pandas as pd

# --- 1. Limpiar: la columna EDAD de los usuarios, tal como llega ---
usuarios = pd.DataFrame({
    "usuario": ["U1", "U2", "U3", "U4", "U5"],
    "edad": ["25", "34", None, "treinta", "450"],
})
usuarios["edad"] = pd.to_numeric(usuarios["edad"], errors="coerce")
usuarios.loc[(usuarios["edad"] < 16) | (usuarios["edad"] > 100), "edad"] = np.nan
usuarios["edad"] = usuarios["edad"].fillna(usuarios["edad"].median())
print(usuarios["edad"].tolist())

# --- 2. Feature engineering: de los visionados a una fila por usuario ---
visionados = pd.DataFrame({
    "usuario": ["U1", "U1", "U1", "U2", "U2", "U3"],
    "fecha":   ["2026-01-10", "2026-02-15", "2026-03-30", "2026-01-20", "2026-03-05", "2026-02-01"],
    "genero":  ["Acción", "Comedia", "Comedia", "Drama", "Drama", "Terror"],
    "minutos": [120.0, 90.0, 90.0, 150.0, 110.0, 95.0],
})
visionados["fecha"] = pd.to_datetime(visionados["fecha"])

features = visionados.groupby("usuario").agg(
    minutos_medios=("minutos", "mean"),
    n_pelis=("minutos", "size"),
    genero_fav=("genero", lambda s: s.mode()[0]),
)
dias = visionados.sort_values("fecha").groupby("usuario")["fecha"].apply(lambda s: s.diff().dt.days.mean())
features["dias_entre_pelis"] = dias
print(features.round(1))

15 · SQL con sqlite3 y paso a Pandas

Para qué sirve Guardar datos en dos tablas relacionadas, hacer la consulta «usuarios de Madrid que han visto más de 1.000 minutos» y recibir el resultado como DataFrame. Usamos SQLite (viene con Python y no necesita instalar nada); con PostgreSQL el SQL sería el mismo y solo cambiaría la forma de conectar.

import sqlite3
import pandas as pd

conn = sqlite3.connect(":memory:")          # una base de datos temporal, solo en memoria
cur = conn.cursor()

cur.execute("CREATE TABLE usuarios (id INTEGER PRIMARY KEY, nombre TEXT, ciudad TEXT)")
cur.execute("CREATE TABLE visionados (id INTEGER PRIMARY KEY, usuario_id INTEGER, minutos REAL)")
cur.executemany("INSERT INTO usuarios VALUES (?, ?, ?)", [
    (1, "Lucía", "Madrid"), (2, "Marco", "Madrid"), (3, "Irene", "Valencia"), (4, "Pablo", "Madrid")])
cur.executemany("INSERT INTO visionados VALUES (?, ?, ?)", [
    (1, 1, 700), (2, 1, 450), (3, 2, 300), (4, 2, 250), (5, 3, 1500), (6, 4, 1200), (7, 4, 80)])

consulta = """
SELECT u.nombre, u.ciudad, SUM(v.minutos) AS minutos_vistos
FROM usuarios AS u
JOIN visionados AS v ON v.usuario_id = u.id
WHERE u.ciudad = 'Madrid'
GROUP BY u.id
HAVING SUM(v.minutos) > 1000
ORDER BY minutos_vistos DESC
"""
df = pd.read_sql_query(consulta, conn)
print(df)
print(df["minutos_vistos"].mean())
conn.close()

22 · Guardar y cargar un modelo con Pickle

Para qué sirve Guardar el modelo ya entrenado en un fichero (modelo.pkl) para usarlo otro día, o desde otro programa, sin volver a entrenar. («Pickle» no es «pepinillo» en este contexto: to pickle es «conservar», como en salmuera.)

import os
import pickle
from sklearn.datasets import load_breast_cancer
from sklearn.model_selection import train_test_split
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.svm import SVC

datos = load_breast_cancer()
X_train, X_test, y_train, y_test = train_test_split(
    datos.data, datos.target, test_size=0.3, stratify=datos.target, random_state=42)

modelo = make_pipeline(StandardScaler(), SVC(C=10, gamma=0.001)).fit(X_train, y_train)

# --- Hoy: guardar el modelo ya entrenado en un fichero ---
with open("modelo.pkl", "wb") as f:
    pickle.dump(modelo, f)
print("¿existe modelo.pkl?", os.path.exists("modelo.pkl"))

# --- Otro día (otro programa): cargarlo y usarlo SIN volver a entrenar ---
with open("modelo.pkl", "rb") as f:
    cargado = pickle.load(f)

iguales = (cargado.predict(X_test) == modelo.predict(X_test)).all()
print("¿mismas predicciones que el original?", iguales)
print("accuracy del modelo cargado:", round(cargado.score(X_test, y_test), 3))
os.remove("modelo.pkl")        # limpieza de este ejemplo

Separar los datos y la palabra clave: generalización

Train, validation y test

No se puede evaluar un modelo con los mismos datos con los que aprendió: sería como ponerle a un alumno en el examen exactamente los ejercicios que ya tenía resueltos en los apuntes. Sacaría un 10 sin haber entendido nada. Por eso se reparten los datos en conjuntos con funciones distintas:

Train (entrenamiento)

Los datos con los que el modelo aprende.

Apuntes y ejercicios.

Validation (validación)

Sirven para tomar decisiones durante el desarrollo: ¿K = 3 o K = 7? ¿100 árboles o 200?

Exámenes de práctica.

Test (prueba)

Se usa una sola vez, al final, para ver cómo rinde el modelo con datos de verdad nuevos.

El examen final.

Un reparto muy habitual es 80 % train y 20 % test (con 1.000 registros: 800 y 200). Se hace con train_test_split, que mezcla los datos al azar antes de dividirlos.

  • random_state=42 fija la «semilla» del azar para que el reparto sea reproducible (cada ejecución da la misma división). El número 42 no es matemáticamente mejor que otro: es una tradición.
  • stratify=y mantiene la proporción de clases. Si el dataset tiene 80 % «No» y 20 % «Sí», tanto train como test tendrán aproximadamente 80/20.
Ojo: data snooping

Si miras el resultado en test, cambias algo, vuelves a mirar test, cambias otra cosa… poco a poco estás adaptando tus decisiones al test y este deja de representar «datos desconocidos». El test se mira al final. Para decidir durante el desarrollo se usa validación (y, mejor, validación cruzada: módulo 5).

Generalización

La idea central de todo el curso

Generalizar es aprender con unos datos y funcionar bien con otros que el modelo nunca ha visto. La meta no es memorizar el entrenamiento: es aprender los patrones.

Hay tres situaciones típicas, que se reconocen comparando el resultado en train y en test:

SituaciónTrainTestQué pasa
Underfitting (infraajuste)61 %60 %El modelo es demasiado simple: ni siquiera entiende los datos de entrenamiento. Sesgo alto.
Buen ajuste86 %84 %Rinde parecido en datos vistos y no vistos: generaliza.
Overfitting (sobreajuste)99 %68 %Ha memorizado ruido y casos particulares del entrenamiento. Varianza alta.
Analogía

Tres amigos te recomiendan películas. Uno memoriza exactamente las que ya has visto y solo te las repite (overfitting): con las películas de siempre acierta, con una nueva no sabe qué decirte. Otro solo sabe que «a todo el mundo le gusta la acción» (underfitting) y se equivoca con casi todo. El que entiende por qué te gustan las que te gustan (generaliza) acierta tanto con las películas conocidas como con los estrenos nuevos.

  • Separar por fechas cuando los datos tienen orden temporal (escena 7 del ciclo de vida, fragmento 11).
  • Rotar el test con la validación cruzada, para no depender de un único reparto de suerte (flujo de Scikit-learn, fragmento 21).

El flujo de Scikit-learn paso a paso

Ya sabes qué es cada etapa de un proyecto. ¿Cómo se ve eso en código de verdad, línea a línea, sin que ningún paso quede en el aire?

Scikit-learn forma parte de un ecosistema: herramientas que trabajan juntas. NumPy y Pandas guardan los datos, SciPy aporta matemáticas, Matplotlib dibuja, y Scikit-learn pone el aprendizaje y las métricas. Lo bueno es que todos sus modelos se usan igual, así que aprender el flujo de uno vale para todos. Lo recorremos de principio a fin.

Paso 1 · X e y: qué entra y qué se quiere saber

Los datos se separan en dos partes. X (mayúscula, porque es una tabla) son las características: lo que el modelo ve. y (minúscula, un vector) es el target: lo que quiere predecir. Un ejemplo (datos inventados) de 4 clientes de una plataforma de vídeo:

Paso 2 · Preprocesar: el escalado

Ya viste por qué las escalas importan. La rutina más común es StandardScaler, que convierte cada columna a «cuántas desviaciones típicas se aleja de su media». Con dos columnas muy distintas:

Ejemplo numérico
  1. Edades 25, 40, 55: media 40; desviación = √((15² + 0 + 15²)/3) = √150 = 12,247.
  2. Edad 25 → (25 − 40) / 12,247 = −1,2247; edad 40 → 0; edad 55 → +1,2247.
  3. Minutos vistos al mes 300, 600, 900: media 600 y desviación 244,95 → −1,2247 · 0 · +1,2247. La misma escala que las edades.

(A veces se simplifica diciendo «−1, 0, 1»: la idea es esa, pero con este método los valores son ±1,2247.) El escalado no cambia la información, cambia su representación numérica. Y ojo, no es reducción de dimensionalidad: después de escalar siguen siendo 3 características; reducir sería pasar de, por ejemplo, 500 a 30.

Paso 3 · Separar train y test

Con 1.000 ejemplos, un reparto 67 % / 33 % deja 670 para entrenar y 330 para probar. La analogía es la del examen: el modelo estudia con 670 preguntas con sus respuestas y se examina con 330 preguntas distintas. Con train_test_split salen cuatro piezas:

PiezaQué esQuién la ve
X_trainCaracterísticas de los ejemplos de estudioEl modelo, al entrenar
y_trainRespuestas de esos ejemplosEl modelo, al entrenar
X_testCaracterísticas de los ejemplos del examenEl modelo, al predecir (sin respuestas)
y_testRespuestas reales del examenSolo tú, para corregir
Ojo: primero separa, luego escala

El escalador calcula medias y desviaciones, y esas medias solo deben salir de X_train (fit_transform en train, transform en test). Si las calculas con todos los datos, información del examen se cuela en el estudio: es otro caso de data leakage.

Paso 4 · Crear el modelo

Elegimos el algoritmo y lo guardamos en una variable: clf = SVC(). (clf es abreviatura de classifier; SVC es un clasificador que verás en el módulo 3.) Pero ojo: crear no es entrenar. En este momento el modelo es una máquina vacía, como un alumno que ha comprado el libro y todavía no lo ha abierto.

Al crearlo puedes dar hiperparámetros: ajustes que tú decides antes de entrenar (en SVC, C y gamma; en el demo de abajo, la tasa de aprendizaje y el número de iteraciones). Son distintos de los parámetros, los números que el modelo aprende durante el entrenamiento. Regla fácil: hiperparámetro = lo configuras; parámetro = lo aprende.

Paso 5 · fit y predict

  • clf.fit(X_train, y_train) = aprender: el modelo estudia los ejemplos y sus respuestas.
  • clf.predict(X_test) = predecir: le damos solo las características del examen y devuelve sus respuestas, y_pred.

Después se comparan y_pred (lo que dijo el modelo) con y_test (la realidad):

y_test (real)y_pred (modelo)
NoNo✅
SíNo❌
SíSí✅
NoNo✅

3 aciertos de 4: accuracy = 3 / 4 = 75 %. Antes de entrenar, predict da error, porque no hay nada aprendido: lo verás en el fragmento 20 (NotFittedError).

Paso 6 · Evaluar: la matriz de confusión

La accuracy cuenta aciertos, pero no dice cómo se equivoca el modelo. Para eso está la matriz de confusión: una tabla que cruza lo real con lo predicho. Con un filtro de spam:

Predice «Spam»Predice «No spam»
Real: SpamTP (verdadero positivo): spam detectadoFN (falso negativo): spam que se nos cuela
Real: No spamFP (falso positivo): correo bueno enviado a spamTN (verdadero negativo): correo bueno que llega

La diagonal (TP y TN) son aciertos; lo demás, los dos tipos de error. Y no pesan igual: en el filtro, un FP (perder un correo importante) es peor que un FN (ver un spam); en un aviso de estrenos es al revés: no avisarte del estreno que esperabas (FN) es peor que avisarte de uno que no te interesa (FP); y en un diagnóstico médico, como el del fragmento 19, dar por sano a un enfermo (FN) es mucho más grave que asustar a un sano (FP). Por eso se usan métricas como precision y recall (módulo 5), que miden cada tipo de error por separado.

Ejemplo numérico: el resultado del fragmento 19

El modelo de cáncer de mama (maligno = «positivo») sobre 171 pacientes de test dio esta matriz: 62 malignos detectados (TP), 2 malignos que dio por benignos (FN), 2 benignos que dio por malignos (FP) y 105 benignos correctos (TN).

  1. Aciertos = 62 + 105 = 167.
  2. Accuracy = 167 / 171 = 0,977.
  3. Hay 2 + 2 = 4 errores, y el que más importa es el FN: 2 pacientes malignos que el modelo tranquilizaría por error.

Paso 7 · Validación cruzada

Si el reparto train/test cae «con mala suerte» (por ejemplo, los casos difíciles solo en test), la nota engaña. La validación cruzada (cross-validation) repite el examen varias veces rotando qué parte se reserva. Con 4 bloques (cv=4):

Prueba 1:  [TEST] [train] [train] [train]
Prueba 2:  [train] [TEST] [train] [train]
Prueba 3:  [train] [train] [TEST] [train]
Prueba 4:  [train] [train] [train] [TEST]
                  ──► 4 notas ──► se combinan (media)

Cada dato se usa para entrenar tres veces y para probar una. En el fragmento 21, las cuatro notas fueron 0,98 · 0,97 · 0,97 · 0,97, con media ≈ 0,972; con cinco bloques (cv=5) la media fue 0,970. Que sean tan parecidas indica que la nota es estable y no un golpe de suerte.

Paso 8 · Hyperparameter Tuning

¿Con qué hiperparámetros funciona mejor el modelo? Se prueban varias configuraciones y se evalúa cada una con validación cruzada. Ejemplo con tres configuraciones inventadas:

ConfiguraciónNota (validación)
A80 %
B87 % ← la mejor
C84 %

Se elige B. GridSearchCV hace esto de forma automática sobre una «rejilla» de valores. En el fragmento 21 probó 9 combinaciones de C y gamma; las notas variaron de 0,703 a 0,980, y la mejor fue C = 10, gamma = 0,001. Pero fíjate en una trampa: el modelo ajustado sacó 0,971 en test, ligeramente peor que el 0,977 del modelo con valores por defecto (un paciente de diferencia entre 171). No es un fallo: los datos ya eran fáciles y la diferencia es ruido. Ajustar hiperparámetros no garantiza una mejora en test; ayuda sobre todo cuando el modelo por defecto va mal.

Paso 9 · Guardar el modelo con Pickle

Entrenar puede tardar horas; no quieres repetirlo cada vez. Pickle convierte el modelo entrenado en un fichero (modelo.pkl) y luego lo vuelve a cargar, otro día o en otro programa, sin reentrenar. (El nombre viene del inglés pickle, «conservar en vinagre»: aquí no tiene que ver con pepinillos, sino con conservar el modelo en un frasco para usarlo después.) El fragmento 22 comprueba que el modelo cargado da las mismas predicciones que el original.

Ojo

Un fichero Pickle puede ejecutar código al cargarse. Carga solo ficheros que hayas creado tú o que vengan de una fuente de confianza.

Dos ejemplos completos

Netflix: «¿le gustará esta película?»

X: género, duración y año de la película, y películas que el usuario ha visto enteras.

y: le gustó / no le gustó (la terminó o la dejó a medias).

Se separa train/test, se crea un clasificador, fit con el pasado, predict para películas nuevas.

Cancelación de una suscripción

X: edad, gasto, horas vistas (la tabla de arriba).

y: canceló sí/no.

Mismo flujo; el resultado alimenta una campaña de retención (¿a quién hacer una oferta?).

  • X + y

El patrón que se repetirá siempre: preparar datos → X + y → train/test → crear modelo → fit() → modelo entrenado → predict() → predicciones → evaluación. Los fragmentos 19 a 22 lo ejecutan con datos reales.

Resumen del módulo

  • Machine Learning = escribir cómo aprender reglas a partir de ejemplos, en vez de escribir las reglas. Entrenar es probar parámetros y quedarse con los que menos se equivocan.
  • IA ⊃ ML ⊃ Deep Learning.
  • Features (X) = lo que el modelo conoce; target (y) = lo que debe predecir. Parámetros los aprende el modelo; hiperparámetros los eliges tú.
  • Tipos de aprendizaje: supervisado (clasificación → categoría, regresión → número), no supervisado, semisupervisado y por refuerzo.
  • Ocho técnicas: clasificación, regresión, clustering, asociación, detección de anomalías (z-score), minería de secuencias, reducción de dimensionalidad y sistemas de recomendación (content-based, collaborative o híbrido, con similitud del coseno).
  • Ciclo de vida en trece escenas: problema → datos → unificar → limpiar → features → EDA → split (por fechas si hay tiempo) → técnica → entrenar → validar → optimizar → evaluar → producción, monitorización y reentrenamiento. El mundo cambia (deriva): un modelo vivo se vigila.
  • Ciencia de Datos (entender, predecir, decidir con tus datos) frente a Ingeniería de IA (construir sistemas sobre modelos preentrenados con prompts, PEFT, RAG y agentes). Casos de uso: descriptivo, predictivo, prescriptivo (valor esperado, optimización) y generativo. RAG busca y pega el documento en el prompt; no reentrena el modelo.
  • Herramientas por capas: Python; SQL, Pandas, NumPy, Spark, Kafka; Matplotlib y Seaborn; SciPy y Scikit-learn; TensorFlow, Keras y PyTorch; OpenCV; NLTK; Hugging Face. No compiten, trabajan juntas.
  • Datos: NaN ≠ 0; imputar con media (datos normales), mediana (outliers) o el más frecuente (categorías); escalar para algoritmos de distancias; One-Hot para categorías sin orden; feature engineering para crear variables más útiles.
  • Reparte en train / validation / test; no mires el test hasta el final; usa random_state y stratify; el escalador se ajusta solo con train.
  • Flujo de Scikit-learn: X + y → train_test_split → crear (≠ entrenar) → fit → predict → evaluar (matriz de confusión: ojo al tipo de error) → validación cruzada → GridSearchCV → Pickle.
  • Generalizar es la meta: buen resultado en datos nunca vistos. Train alto + test bajo = overfitting; los dos bajos = underfitting.
