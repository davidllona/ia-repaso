Escena 8: ¿cómo recomendar? Dos ideas que todos usamos sin darnos cuenta:

Content-based

«Te gusta X → te gustan cosas parecidas a X.» Mira los rasgos de las películas. El dependiente del videoclub que te enseña más de miedo.

Collaborative

«Las personas parecidas a ti también vieron…» Mira lo que han visto otros. El amigo con tus mismos gustos.

Con números: ¿cuánto se parece David a B?

Ejemplo numérico (similitud del coseno)

Seis películas (Matrix, E.T., Indiana Jones, Iron Man, Thor, Shrek); cada persona es un vector de 1 (vista) y 0.

  1. David = (1, 1, 1, 0, 0, 0) y B = (1, 1, 1, 0, 1, 0).
  2. Producto escalar: 1·1 + 1·1 + 1·1 + 0 + 0 + 0 = 3.
  3. Longitudes: |David| = √3 ≈ 1,732 · |B| = √4 = 2.
  4. cos(David, B) = 3 / (1,732 × 2) = 0,87. Con C (solo Shrek): 0.

B vio Thor y David no → Thor puntúa 0,87 en collaborative. No es una probabilidad: es un ranking.

Al final se evalúa con el test una sola vez (10.000 recomendaciones → 1.000 clics → 200 películas terminadas). Y empieza la escena que no acaba: producción.

En tres líneas

  • Primero el problema y el número con que medirás la mejora; el algoritmo llega en la escena 8 de 13.
  • Content-based mira los rasgos de las películas; collaborative, a la gente parecida; los reales son híbridos.
  • Con datos temporales, el test es el futuro. Tras desplegar: monitorizar y reentrenar, porque los hábitos derivan.

12 · Recomendador content-based y collaborative con similitud del coseno

Para qué sirve Construir a mano los dos grandes tipos de recomendador sobre una matriz usuario × película pequeña, ver qué recomienda cada uno y combinarlos en un híbrido. Es el mismo cálculo que hace el experimento de la sección anterior.

import numpy as np
import pandas as pd

peliculas = ["Matrix", "E.T.", "Indiana Jones", "Iron Man", "Thor", "Shrek"]
usuarios = ["David", "B", "C", "D"]

# Matriz usuario x película: 1 = la ha visto
vistas = pd.DataFrame(
    [[1, 1, 1, 0, 0, 0],      # David
     [1, 1, 1, 0, 1, 0],      # B: lo mismo que David y además Thor
     [0, 0, 0, 0, 0, 1],      # C: solo Shrek
     [1, 1, 0, 1, 0, 0]],     # D: Matrix, E.T. e Iron Man
    index=usuarios, columns=peliculas)

# Características de cada película: [Acción, Ciencia ficción, Aventura, Superhéroes, Comedia]
rasgos = pd.DataFrame(
    [[1, 1, 0, 0, 0],   # Matrix
     [0, 1, 0, 0, 0],   # E.T.
     [1, 0, 1, 0, 0],   # Indiana Jones
     [1, 1, 0, 1, 0],   # Iron Man
     [1, 1, 0, 1, 0],   # Thor
     [0, 0, 0, 0, 1]],  # Shrek
    index=peliculas, columns=["Acción", "Ciencia ficción", "Aventura", "Superhéroes", "Comedia"])

def coseno(a, b):
    return a @ b / (np.linalg.norm(a) * np.linalg.norm(b))

# --- Content-based: "te gusta X -> cosas parecidas a X" ---
perfil = rasgos.loc[vistas.loc["David"] == 1].mean()      # gustos medios de David
content = rasgos.apply(lambda fila: coseno(perfil.values, fila.values), axis=1)

# --- Collaborative: "personas parecidas a ti también vieron..." ---
yo = vistas.loc["David"].values
parecido = vistas.apply(lambda fila: coseno(yo, fila.values), axis=1).drop("David")
collab = (vistas.drop("David").T * parecido).T.sum()

nuevas = vistas.loc["David"] == 0                          # solo lo que aún no ha visto
print("Parecido de David con los demás:", parecido.round(2).to_dict())
tabla = pd.DataFrame({"content": content[nuevas], "collab": collab[nuevas]}).round(2)
tabla["collab_norm"] = (tabla["collab"] / tabla["collab"].max()).round(2)
tabla["hibrido"] = (0.5 * tabla["content"] + 0.5 * tabla["collab_norm"]).round(2)
print(tabla.sort_values("hibrido", ascending=False))

13 · Monitorización: deriva de datos y reentrenamiento

Para qué sirve Simular lo que pasa tras llevar un modelo a producción: los hábitos de los clientes cambian mes a mes, el modelo congelado empeora y reentrenarlo con datos recientes lo arregla.

import numpy as np
from sklearn.tree import DecisionTreeClassifier

rng = np.random.default_rng(7)

def clientes_del_mes(umbral_real, n=400):
    """Días sin entrar de n clientes y si cancelaron. Cancelar = pasar del umbral (con un 5 % de ruido)."""
    dias = rng.uniform(0, 60, n)
    cancela = (dias > umbral_real).astype(int)
    ruido = rng.random(n) < 0.05
    return dias.reshape(-1, 1), np.where(ruido, 1 - cancela, cancela)

# Los hábitos cambian: cada mes la gente cancela con menos días sin entrar
umbrales = [20, 20, 18, 15, 12, 10]
meses = [clientes_del_mes(u) for u in umbrales]

# Mes 0: entrenamos y lo ponemos en producción
modelo = DecisionTreeClassifier(max_depth=1, random_state=0).fit(*meses[0])
print(f"Entrenado en el mes 0: umbral aprendido = {modelo.tree_.threshold[0]:.1f} días")

# Monitorización: con el modelo congelado, ¿cuánto acierta cada mes?
for mes, (X, y) in enumerate(meses):
    print(f"mes {mes}: accuracy = {modelo.score(X, y):.3f}")

# Reentrenamiento con los datos recientes (meses 4 y 5)
X_rec = np.vstack([meses[4][0], meses[5][0]])
y_rec = np.concatenate([meses[4][1], meses[5][1]])
nuevo = DecisionTreeClassifier(max_depth=1, random_state=0).fit(X_rec, y_rec)
X6, y6 = clientes_del_mes(10)
print(f"Reentrenado: umbral = {nuevo.tree_.threshold[0]:.1f} días")
print(f"mes 6, modelo viejo = {modelo.score(X6, y6):.3f} | modelo nuevo = {nuevo.score(X6, y6):.3f}")

El ciclo de vida de un proyecto de Machine Learning

Tu jefe en StreamFlix dice: «queremos que la gente vea más películas y series». ¿Por dónde empiezas? ¿Abres un cuaderno de Python y pruebas algoritmos?

No. Un proyecto real no empieza eligiendo un algoritmo: es una película con trece escenas, y la mayoría tienen que ver con los datos y con lo que ocurre después de entrenar. Vamos a recorrerlas todas con un único ejemplo, una plataforma de streaming (la llamaremos StreamFlix), para ver cómo se pasa de una frase vaga a un recomendador de películas funcionando.

Analogía

Rodar una película. Primero decides qué historia cuentas y para quién (problema); reúnes el equipo y el material (datos); revisas y limpias lo rodado (preparación); pruebas distintos montajes (modelos); cuando uno convence se lo enseñas a un público de prueba que no la ha visto antes (test); la estrenas en los cines (producción); y sigues leyendo críticas y mirando la taquilla para cambiar lo que haga falta (monitorización y mejora). Ni el mejor director se salta la revisión del material rodado.

Dos ideas que conviene grabarse antes de empezar:

  • El modelo suele ser la parte más corta. Entender, limpiar y preparar los datos es donde se invierte casi todo el tiempo, y donde más se gana o se pierde calidad. Y lo que ocurre después de entrenar (vigilarlo) dura todo lo que viva el proyecto.
  • El proceso no es lineal. Cuando evalúas y el resultado no convence, vuelves atrás: más datos, mejores features, otro algoritmo… Por eso la última escena enlaza otra vez con la primera.

Escena 1 · Definir el problema

El proyecto nace de un objetivo de negocio y hay que traducirlo a una pregunta que un modelo pueda responder:

OBJETIVO DE NEGOCIO:   «queremos que se vea más contenido»
          │   (demasiado vago: ¿qué predigo? ¿con qué datos?)
          ▼
PROBLEMA DE ML:        «recomendar películas y series relevantes según
                        lo que cada usuario ve y busca»

Con esa frase ya sabemos qué técnica nos interesa (un sistema de recomendación), qué datos necesitaremos (lo que ve y busca cada usuario) y cómo sabremos si funciona (¿hacen clic en las recomendaciones? ¿terminan de ver más películas?).

Ojo

Un problema mal definido es el error más caro, porque no se nota hasta el final: puedes construir un modelo precisísimo que responda a una pregunta que a nadie le importa. Antes de tocar datos, escribe qué decisión mejorará el modelo y con qué número vas a medir que ha mejorado.

Ojo: la explosión de filas

Al unir tablas «uno a muchos» sin cuidado se duplican filas. Si un usuario tiene 3 visionados y 2 favoritos y los cruzas directamente, salen 3 × 2 = 6 filas para ese usuario, y sus minutos vistos se cuentan el doble. Comprueba siempre el número de filas antes y después de cada unión.

Escena 4 · Preparar y limpiar

Los datos reales llegan sucios. En StreamFlix, la columna EDAD contiene:

EDAD:   25    34    NULL    «treinta»    450

Un hueco, un texto en vez de un número y una edad imposible. Y hay más: usuarios duplicados, películas sin género, duraciones imposibles (0 min o 9.999 min) y fechas con formatos distintos (12/03/2026, 2026-03-12, 12 mar 2026). Cada problema tiene su tratamiento (valores faltantes, outliers, formatos), que ya conoces de «Preparar los datos». El fragmento 10 limpia justo esta columna: convierte a número, anula lo imposible (NaN) e imputa con la mediana.

Escena 6 · Explorar los datos (EDA)

EDA significa Exploratory Data Analysis, «análisis exploratorio de datos»: mirar los datos con gráficos y estadísticas antes de modelar, para encontrar patrones, relaciones, errores, tendencias y correlaciones. Es como ver el material rodado antes de montar la película: descubres que faltan tomas, que algunas salen desenfocadas y que ciertas escenas van siempre juntas.

En StreamFlix, un EDA podría descubrir: «quien ve Harry Potter 1 ve la segunda en los 7 días siguientes». Es una pista oro para el recomendador. El fragmento 11 lo comprueba con datos de juguete: de 3 usuarios que vieron la primera, 2 vieron la segunda en 7 días o menos (4 y 3 días), y uno tardó 8.

Ojo

El EDA no se salta aunque tengas prisa: si no miras los datos, no descubres hasta el final que la mitad de las fechas estaban en el año 1970 o que un solo usuario con la tele puesta todo el día distorsiona los minutos medios. Y recuerda que una correlación (las dos películas se ven seguidas) no prueba causa: quizá, simplemente, son una saga.

Escena 7 · Separar train y test (aquí, por fechas)

Ya vimos que hay que reservar datos para probar el modelo («Separar los datos»). Normalmente se reparte al azar, pero cuando los datos tienen orden temporal hay que respetarlo. Ejemplo con las películas que ve un usuario:

10 enero   → ve Harry Potter 1     ┐
14 enero   → ve Harry Potter 2     ├─ TRAIN (el pasado, lo que el modelo conoce)
12 febrero → ve Harry Potter 3     ┘
2 abril    → ve Harry Potter 4 ─── TEST (el «futuro» que debe acertar)

Así probamos el modelo como lo usaremos en la vida real: con datos posteriores a los que vio al entrenar. El fragmento 11 hace este corte por fecha (10 visionados hasta marzo, 1 visionado de abril).

Ojo

Si mezclaras al azar, un visionado de abril podría acabar en el train y uno de marzo en el test: el modelo aprendería con el futuro para predecir el pasado. Es una forma de data leakage (módulo 5) y da resultados bonitos que no se repetirán.

Escena 8 · Elegir la técnica: content-based, collaborative o híbrido

Quieres recomendar a David una película que aún no ha visto. ¿En qué te basas?

Hay dos ideas, muy distintas, que cualquier persona usa sin darse cuenta:

Content-Based Filtering

«Te gusta X → te gustan cosas parecidas a X.»

Mira las características de las películas. Si David ha visto Matrix, recomendamos películas con rasgos parecidos a las que ya vio.

Analogía: el dependiente del videoclub que, al ver que alquilas una de miedo, te enseña otras de miedo.

Collaborative Filtering

«Las personas parecidas a ti también vieron…»

Mira el comportamiento de otras personas. David y el usuario B han visto cosas parecidas; B vio Thor; se la recomendamos a David.

Analogía: pedir consejo a un amigo con tus mismos gustos.

El ejemplo, con números

Cuatro personas y seis películas (✓ = la ha visto). Para medir «parecido» usamos la similitud del coseno. Cada fila es un vector (1 = vista, 0 = no) y el coseno compara su dirección:

\[ \cos(a, b) = \frac{a \cdot b}{\lVert a \rVert \, \lVert b \rVert} \]

donde \( a \cdot b \) es el producto escalar (se multiplican posición a posición y se suma), y \( \lVert a \rVert \) la longitud del vector (la raíz de la suma de sus cuadrados). Vale 1 si los dos vectores señalan exactamente en la misma dirección (gustos idénticos) y 0 si no coinciden en nada.

Ejemplo numérico: ¿cuánto se parece David a B? ¿Y a D?
  1. David = (1, 1, 1, 0, 0, 0) y B = (1, 1, 1, 0, 1, 0).
  2. Producto escalar: 1·1 + 1·1 + 1·1 + 0 + 0 + 0 = 3.
  3. Longitudes: |David| = √3 ≈ 1,732 · |B| = √4 = 2.
  4. cos(David, B) = 3 / (1,732 × 2) = 0,87.
  5. Con D = (1, 1, 0, 1, 0, 0): producto escalar 2 y longitudes √3 y √3, cos = 2 / 3 = 0,67. Con C (solo Shrek): producto escalar 0, cos = 0.
Ejemplo numérico: las dos recomendaciones

Collaborative. Cada película que David no ha visto puntúa sumando el parecido de quienes la vieron.

  1. Thor: la vio B (0,87) → puntuación 0,87.
  2. Iron Man: la vio D (0,67) → puntuación 0,67.
  3. Shrek: solo C, cuyo parecido es 0 → 0.

Content-based. El «perfil» de David es la media de los rasgos de lo que vio: Matrix (Acción, Ciencia ficción), E.T. (Ciencia ficción) e Indiana Jones (Acción, Aventura) → (Acción, Ciencia ficción, Aventura, Superhéroes, Comedia) = (2/3, 2/3, 1/3, 0, 0). Para Iron Man, con rasgos (1, 1, 0, 1, 0), cos = (4/3) / (1 × √3) = 0,77; para Thor, los mismos rasgos, 0,77; para Shrek, 0.

Compara: el content-based no puede elegir entre Iron Man y Thor (son películas con idénticos rasgos), pero el collaborative sí, porque alguien muy parecido a David ya vio Thor. Y el collaborative necesita que haya gente parecida; el content-based no. Cada uno tiene su punto débil:

Content-basedCollaborative
Se basa enrasgos de las películaslo que han visto otras personas
Idea«cosas parecidas a lo que te gustó»«gente como tú también vio…»
Punto fuertefunciona con películas nuevas y con pocos usuarios; es fácil de explicardescubre gustos que no están en los rasgos («quien ve X, sorprendentemente, ve Z»)
Punto débilsolo recomienda más de lo mismo; no sorprendeno funciona sin historial (cold start): una película o un usuario nuevos no tienen datos

Por eso los sistemas reales son híbridos: mezclan las dos puntuaciones (la de collaborative se normaliza para que ambas estén en 0–1) y así cada una tapa los huecos de la otra. Con una mezcla al 50 %: Thor = 0,5 × 0,77 + 0,5 × 1,00 = 0,88; Iron Man = 0,5 × 0,77 + 0,5 × 0,77 = 0,77. Gana Thor.

Ojo

El número 0,87 no es una probabilidad de que le guste: es un ranking. Sirve para ordenar candidatos, no para decir «a David le gustará con un 87 % de seguridad». Y un buen recomendador no debe ofrecer lo que ya se ha visto (por eso se filtran las películas vistas). El fragmento 12 repite estas cuentas con Pandas.

Escena 9 · Entrenar

En un clasificador, entrenar es llamar a fit. En un recomendador basado en vecinos como el de arriba, entrenar es calcular las similitudes entre películas y entre personas a partir de los datos de train: esa tabla de parecidos es «lo aprendido». En otros modelos (redes neuronales, factorización de matrices) hay parámetros que se ajustan iterativamente, como en el módulo 2. En todos los casos la regla es la misma: solo se usan datos de train.

Escena 10 · Validar

Tenemos tres candidatos (content-based, collaborative, híbrido). ¿Cuál es mejor? No se puede decidir con el test (si lo miras para elegir, ya no es un examen sorpresa). Se usa un conjunto de validación o, mejor, validación cruzada: probar con varias porciones distintas de los datos de train, rotando. El fragmento 21 lo hace con un clasificador real (cross_val_score); en el módulo 5 lo verás en profundidad.

Escena 11 · Optimizar

Cada enfoque tiene sus hiperparámetros: cuánto pesa el content-based en el híbrido (el slider del experimento de arriba), cuántas personas parecidas miramos (K), qué mínimo de parecido exigimos… Se prueban combinaciones y se compara con validación: es el hyperparameter tuning. En scikit-learn lo hace GridSearchCV (fragmento 21: probó 9 combinaciones de C y gamma y notas entre 0,703 y 0,980).

Escena 12 · Evaluar con datos nunca vistos

Con el modelo elegido y ajustado, se abre por fin el «cajón» del test, una sola vez. Para un recomendador, las métricas son de negocio: se muestran recomendaciones y se miden los resultados.

Ejemplo numérico
  1. Se muestran 10.000 recomendaciones (cifras inventadas).
  2. Reciben 1.000 clics: tasa de clics = 1.000 / 10.000 = 10 %.
  3. De esos clics, 200 acaban viendo la película entera: conversión = 200 / 1.000 = 20 %.
  4. De extremo a extremo: 200 / 10.000 = 2 % de las recomendaciones acaban en una película vista hasta el final.

Esa cifra solo significa algo comparada con algo: ¿cuánto se veía sin recomendador? ¿Y con otro enfoque? Evaluar es siempre comparar.

Escena 13 · Producción, monitorización y reentrenamiento

Un modelo que se queda en un cuaderno de Jupyter no vende nada. Esta última escena tiene tres partes y no termina nunca:

  1. Deployment (despliegue): llevar el modelo a producción. En StreamFlix, el bloque «Porque viste…» de la portada llama al modelo cada vez que alguien entra (a menudo a través de una API). Guardar el modelo en un fichero (Pickle, fragmento 22) es el primer paso.
  2. Monitorización: vigilarlo cada día: clics, películas terminadas, errores, calidad de las recomendaciones… y, sobre todo, ¿han cambiado los hábitos de los espectadores?
  3. Reentrenamiento: aparecen películas nuevas, usuarios nuevos y tendencias nuevas que el modelo no conoce. Se vuelve a entrenar con datos recientes y se despliega de nuevo.

¿Por qué se degrada un modelo que «no ha cambiado»? Porque el mundo sí cambia. A esto se le llama deriva (drift): los datos de hoy ya no se parecen a los de entrenamiento. Mira el efecto:

El fragmento 13 hace exactamente esto con scikit-learn: un modelo que empieza acertando el 95,8 % cae al 76,0 % en el mes 5; en el mes 6, el modelo viejo marca 79,0 % y el reentrenado con los datos recientes, 91,2 %. Toda la película se resume en una frase y en un bucle:

Problema → Datos → Preparación → Entrenamiento → Evaluación → Producción → Monitorización → Mejora
   ▲                                                                                              │
   └──────────────────────────────────────────────────────────────────────────────────────────────┘
Lo que debo recordar
  • Un modelo malo con datos buenos se arregla; un modelo bueno con datos malos casi nunca.
  • El objetivo final no es acertar con los datos de entrenamiento, sino con datos nuevos, y hoy y dentro de seis meses.
  • Un modelo en producción es un producto vivo: se monitoriza y se reentrena.
